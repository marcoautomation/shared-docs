FEARLESS DEVELOPMENT AND VERIFICATION GUIDE
For any human or AI agent working on this codebase, on any OS.
================================================================

THE REPOSITORIES

Fearless is a programming language and its toolchain, split across four
git repositories that must be checked out as SIBLING directories (all
direct children of one common parent folder) for anything here to build:

  Commons          shared, dependency-free Java utilities. Everything
                   else depends on this; it depends on nothing here.
  Frontend         the Fearless language frontend (parser, name
                   resolution, type inference). Depends on Commons.
  Coordinator      the compiler backend, CLI, and the desktop project
                   manager GUI. Depends on Commons and Frontend. Almost
                   everything in this guide lives here, under
                   Coordinator/test/mainCoordinator/.
  StandardLibrary  Fearless SOURCE code, not Java: the language's own
                   base library ("base"), its runtime ("rt"), and a
                   folder of integration-test Fearless projects. This is
                   compiled and run BY Coordinator, not built with javac.

All four are at https://github.com/FearlessLang/<name>.

CHECKING THEM OUT

Clone all four into one parent directory, e.g.:

  mkdir fearless-workspace && cd fearless-workspace
  git clone https://github.com/FearlessLang/Commons.git
  git clone https://github.com/FearlessLang/Frontend.git
  git clone https://github.com/FearlessLang/Coordinator.git
  git clone https://github.com/FearlessLang/StandardLibrary.git

(To contribute: fork each repository first and clone your fork, adding the
FearlessLang original as a remote named "upstream" - pull requests must
target the FearlessLang original, never your own fork.)

Line endings matter: the repositories carry LF-committed sources, and some
tests compare generated output against expected text byte for byte. Run
`git config core.autocrlf false` in each before checking out on a platform
that would otherwise rewrite line endings (this matters on Windows; it is
a no-op elsewhere).

THE LocalResources FILE

Coordinator/test/mainCoordinator/ contains the Java programs described
below, and they need to know, as absolute paths, where each repository's
relevant folders live on your disk. Those paths differ machine to machine,
so they are not committed: `Coordinator/test/mainCoordinator/
LocalResources.java` is gitignored, and you create it yourself, once, per
checkout.

A template sits right next to it:
`Coordinator/test/mainCoordinator/LocalResourcesTemplate.java`. Copy it to
`LocalResources.java` in the same folder, rename the class from
`LocalResourcesTemplate` to `LocalResources`, and set the one `prefix`
field to the parent directory you cloned the four repositories into. Every
other field is derived from that single `prefix` and should not normally
need touching:

  stLibPath             StandardLibrary/base        (the language's own library)
  stLibRTPath            StandardLibrary/rt           (its runtime)
  stLibDebugOut          StandardLibrary/dbgOut       (build cache/output)
  integrationTests      StandardLibrary/integrationTests (example Fearless projects)
  commonsSrc             Commons/src
  frontendSrc            Frontend/FearlessFrontend/src
  frontendSrcModule     Frontend/FearlessFrontend/srcModule
  coordinatorSrc         Coordinator/src
  coordinatorSrcModule  Coordinator/srcModule
  portableFolderOut     StandardLibrary/fearlessArtefact        (built app-image output)
  managedFolderOut      StandardLibrary/fearlessManagedArtefact (built app-image output)
  badZipCorpous          Coordinator/badZips
  packaging              Coordinator/_fearless_packaging

Nothing here is committed back; you (or your tooling) recreate this file
by hand for every new checkout.

THE FIVE JAVA PROGRAMS

Everything below lives in `Coordinator/test/mainCoordinator/` and is a
plain, ordinary `.java` file - none of it needs a separate compile step
you run yourself. This relies on a JDK recent enough to run a multi-file
Java program directly (`java SomeFile.java`, which transparently compiles
that file and whichever sibling `.java` files it needs); this project is
built and tested on JDK 26. If `java SomeFile.java` fails saying it can't
resolve a sibling file, your JDK predates this capability and needs
upgrading. Run each of these from inside `Coordinator/test`:

  java --module-path ../../Commons/Commons.jar --add-modules Commons \
       mainCoordinator/<Name>.java [arguments]

`Commons.jar` is committed to the Commons repository itself (unlike
everything else it builds, which is gitignored) specifically so it is
present and ready immediately after cloning or updating - it is the one
thing every one of these five programs needs already built, because each
of them uses it, as a real Java module via `--module-path`/`--add-modules`
(not a plain classpath entry - that would defeat the point of the strict,
real-module compilation described below), to compile everything else on
the fly.

  FrontendOnly.java
    Builds Commons and Frontend and runs Frontend's test suite. Fast -
    seconds, not minutes. Takes one argument, described below.

  CoordinatorMinusIntegration.java
    Builds Commons, Frontend, and Coordinator, and runs Coordinator's test
    suite EXCLUDING its slow `integrationTests` package (which compiles
    and actually runs whole example Fearless programs, one JVM launch per
    project). Fast. Same argument as above. Note: this does not build the
    Fearless standard library's own "base" cache - the only thing that
    does that is `integrationTests`' own setup, which this program skips.
    A separate, unrelated test (`testBuildBase.TestBuildBase`) does its
    own one-off compile of base as part of this same run; that is not the
    same thing and does not populate any shared cache.

  FullAutoTests.java
    Builds and runs everything FrontendOnly and CoordinatorMinusIntegration
    do, PLUS Coordinator's `integrationTests` package. Slow - minutes, not
    seconds. Same argument as above. Does not build or publish any
    application image; that is the next two programs' job.

  DeployPortableFearless.java
    Builds a self-contained, runnable application image of the Fearless
    compiler/runner (the "portable" build). No arguments. Noticeably
    slower than the test programs above - it also invokes jlink and
    jpackage.

  DeployManagedFearless.java
    Builds a self-contained, runnable application image of the Fearless
    project manager GUI. No arguments. Same caveats as
    DeployPortableFearless.java.

Every compile in all five of these enables the strictest practical
javac warnings (`-Xlint:all`, minus two categories - `auxiliaryclass` and
`missing-explicit-ctor` - that fire constantly on this codebase's
deliberate style of small same-file helper classes and static-only utility
classes, and were judged not worth changing that style for) with
`-Werror`, so a real compiler warning fails the build exactly like an
error would, and real JPMS modules throughout, so a class quietly missing
from a module's `requires`/`exports` fails to compile instead of silently
working on a classpath and only breaking when something eventually tries
to actually package this as a module.

The three test programs above take one argument: the path to a directory
containing these jars (all on Maven Central; the versions below are what
this codebase is currently tested against - newer patch releases are
likely fine):

  org.junit.jupiter:junit-jupiter-api:6.1.3
  org.junit.platform:junit-platform-commons:6.1.3
  org.junit.platform:junit-platform-console-standalone:6.1.3
  org.opentest4j:opentest4j:1.3.0
  org.apiguardian:apiguardian-api:1.1.2
  org.jspecify:jspecify:1.0.0

(Coordinator's own runtime dependencies - a JDBC driver, a graphics
library, and so on - are already checked into `Coordinator/externalJars/`
and need no separate download.)

WHAT A FULL MANUAL CHECK SHOULD DO

Beyond the five programs above, this project benefits from a deeper,
periodic verification pass. It doesn't need to be run by any particular
tool - a human, a script, or an AI agent can all do this - but it should
cover the following, in order, stopping and reporting clearly at whichever
step fails rather than pushing on regardless:

  1. Bring the checkout to the current state of each repository's main
     branch (fetch and reset all four to their upstream main), so the
     check reflects the project as it actually is today, not leftover
     local state.
  2. Run FullAutoTests.java. If it fails, stop: there is no value in doing
     any of the following against a build that doesn't even pass its own
     automated suite.
  3. If that passed, exercise the manager GUI by hand (or however your
     environment can drive a GUI) against its published acceptance test
     plan (https://marcoautomation.github.io/shared-docs/manager-gui-tests.txt),
     since no automated harness in this repository covers GUI behavior.
     Record what you find - especially any failure, with enough detail
     (what was expected, what happened) that someone else could reproduce
     and fix it without re-running the whole plan themselves.
  4. Finally, think of ONE way to exercise this project that nothing above
     already covers, and actually do it - not a variation on an existing
     test, a genuinely different angle: a malformed or unusual program the
     parser has never seen, a much larger or more deeply nested project
     than anything in the existing examples, an environment or platform
     detail the scripted tests don't touch, a manager workflow the GUI
     plan doesn't exercise, something about the built application image
     itself rather than the source it runs. Before picking one, check
     https://marcoautomation.github.io/shared-docs/fearless/exploratory-checks.txt
     for what's already been tried, so successive checks broaden coverage
     instead of repeating each other. If what you tried passes, add a
     dated entry to that same log describing what you checked and how. If
     it turns up a real problem, do not silently fix it or add a test on
     your own judgment - report it clearly, with enough detail to
     reproduce, so a maintainer can decide how it should become a
     permanent regression test.
