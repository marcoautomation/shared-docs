Fearless Manager — GUI test plan

Scripted acceptance tests for the desktop manager (manager.ManagerMain, the fearlessManaged app-image): concrete mouse/keyboard steps and the exact result expected after each one, written so they can be run by a person today and by a Claude agent driving the real GUI later — screenshot, click, screenshot, compare. Read the note on terminology below if the vocabulary here is unfamiliar.

Status: draft — written from reading the source, not yet executed against a running manager. Status: verified — executed at least once, actual result matched expected. Status: failing — executed, actual result diverged; see its note.

What this document is

In software engineering, a scripted sequence of user actions paired with the result each one should produce is a test case (or test script), and a collection of them aimed at one release is a test plan — the practice historically called manual acceptance testing or UAT. Writing each step as "do X → expect Y" is the same shape as Given/When/Then (Gherkin/BDD) scenarios. What is new is who runs them: instead of a person clicking through the app before a release, an agent drives the real, on-screen GUI — launching the process, sending mouse and keyboard events, taking screenshots, and comparing them against the expected results below. That is standard GUI test automation / end-to-end (E2E) testing; for a Swing app specifically the well-known tooling is AssertJ-Swing (formerly FEST-Swing), though driving the OS-level screen and input queue works too and matches how a human tester would actually see it.

Every test case below is deliberately concrete about paths, labels and exact strings taken from the current source, so that "did it pass" is a fact, not a judgment call. Where the source didn't settle a detail (mainly: is the default window big enough), the test says so explicitly and asks for a judgment call rather than inventing a number.

Fixtures

  • Manager build. Unzip fearless-manager-windows-x64.zip anywhere; the app-image folder is named fearlessManaged<version> (currently 0_001), and the executable inside it is fearlessManaged<version>.exe.
  • Manager data folder. The manager keeps its state — registered.txt (the registered project list), instance.lock, and the messages\ drop folder — in a sibling folder named fearless<version>, next to wherever fearlessManaged<version> was unzipped. This is "the manager folder" referred to throughout.
  • hello_world project. From fearless-examples.zip, folder 01_hello_world, marker file hello_world.fearless (registers in the manager under the name hello_world). It compiles to exactly five runnable mains, alphabetically: Hello1, Hello3, Hello4, Hello5, Hello6. Hello1 prints a literal string; Hello3/Hello4 print lists; Hello5 prints a mapped/flowed list; Hello6 deliberately raises an error (Error.msg`AAAAh`) and should exit non-zero with a stack trace ending in AAAAh.
  • A second, disposable console project for tests that need two registered projects — the examples zip's 02_mains_in_methods (registers as mains_in_methods) works and compiles quickly.
  • A GUI-kind project that never exits on its own, for the "something is running" tests — e.g. 09_gui_basics (registers as gui_basics).

Clean start (run before Test 1, and whenever a test says "from a clean start")

  1. If fearlessManaged<version>.exe is running, quit it: Manager menu → Quit manager (not just closing the window — see Test 6 for why that distinction matters).
  2. Delete the manager data folder (fearless<version>, see Fixtures above).
  3. Delete hello_world's .fearless_out cache folder, next to hello_world.fearless.
  4. Only for Test 1: make sure no Fearless build currently owns the .fearless extension — if a previous run associated it, run Test 1's steps 4–5 once first (or forget the association by hand in Windows' "Default apps" settings) so Test 1 exercises a genuine first-time registration rather than a no-op.

Tests

Test 1 First-run file association, and forgetting it draft

Preconditions: clean start done; nothing owns the .fearless extension yet.
#ActionExpected result
1Open a Windows Explorer window on the 01_hello_world folder, so hello_world.fearless is visible.The file shows Explorer's generic/unregistered file icon — nothing Fearless-specific yet.
2Double-click fearlessManaged0_001.exe (no arguments).The Manager window opens. No dialog appears about the association — claiming .fearless is silent and automatic on this first run (only forgetting it, step 4, asks for confirmation).
3Switch back to the Explorer window from step 1. Press F5 if it hasn't updated within a few seconds.hello_world.fearless now shows the Fearless icon.
4In the Manager, open Manager → Forget association. A Yes/No dialog appears asking to remove Fearless as the registered opener for Fearless projects. Click Yes.The dialog closes, and — this is a real side effect, confirm it deliberately — the Manager window closes too: forgetting the association quits the whole manager process.
5Switch back to Explorer, F5 if needed.hello_world.fearless has lost the Fearless icon, back to the generic one.
6Double-click fearlessManaged0_001.exe again.The Manager window opens again, with the project list exactly as the manager data folder still records it (association isn't the same thing as the registered-project list).
7Switch back to Explorer, F5 if needed.hello_world.fearless shows the Fearless icon again.

Test 2 Project panel split view, and the collapsible divider draft

Preconditions: Manager open, nothing registered yet (fresh from Test 1, or a clean start).
#ActionExpected result
1With the Manager window open and empty, observe the layout.Only the "Registered project folders" icon grid is visible, filling the window — no project panel, no divider.
2Project → Add folder..., browse to and select 01_hello_world, click Open.A hello_world tile appears in the icon grid, badged "needs compiling" (no cache yet, per the clean start).
3Click the hello_world tile.The window splits: the icon grid moves to a narrower left pane, and a right pane appears showing hello_world's header, an "Information" panel, a "Mains to run" panel, tool buttons, and an empty Output area — with a visible vertical divider between the two panes.
4Press the mouse down on the divider and drag it left, then right.The split moves live with the mouse: dragging left widens the right (project) pane, dragging right widens the left (icon) pane. Release re-anchors it at the new position.
5Drag the divider close enough to the window's right edge that the right pane is left with (near) no width.The window effectively shows only the icon grid; the project pane is squeezed to a sliver. The icon grid stays fully usable at this width — e.g. clicking the hello_world tile still works.

Test 3 Compile and run all mains; output completeness draft

Preconditions: hello_world registered (Test 2), its .fearless_out cache deleted, its panel open.
#ActionExpected result
1Click Compile.Output immediately shows --- compiling hello_world ---; Compile/Run selected are disabled while busy. On completion: --- compile done ---, the "Mains to run" list fills with 5 checkboxes — Hello1, Hello3, Hello4, Hello5, Hello6 — and the Information panel's "Compiled cache" line reads "up to date" with a real "Last compile" timestamp.
2Click the small All button above the mains list.All 5 checkboxes become checked.
3Click Run selected.For each of the 5 mains, in order: Output appends --- running <name> ---, then that main's own printed output, then --- <name> exited with <code> after <N>s ---. Hello1/3/4/5 exit 0; Hello6 prints an error and stack trace containing AAAAh before exiting non-zero.
4Once all 5 have run, read the Output area top to bottom (scroll to the very top, then to the very bottom).All 5 run blocks are present in full — nothing silently truncated or missing — whether that requires scrolling or not.
5Design check, not just an execution check: judge whether the default window (760×620) and Output area (a 10-row JTextArea) comfortably show this entire 5-main run without the user having to resize anything by hand.If it does not, record that as a finding against FolderInfo/ManagerGui's defaults — candidate fixes: a taller default Output area, remembering the user's last window size, or a one-click "maximize output" toggle. Don't silently accept scrolling as good enough for a first impression.

Test 4 A second project, and switching between them draft

Preconditions: hello_world registered and compiled (Test 3).
#ActionExpected result
1Project → Add folder..., select 02_mains_in_methods.A second tile, mains_in_methods, appears alongside hello_world; badges are independent — hello_world "up to date" (green-ish), mains_in_methods "needs compiling".
2Click the mains_in_methods tile.The right pane switches to mains_in_methods' own header/info/mains/output.
3Click back on the hello_world tile.The pane switches back; hello_world's Output area still shows the full run log from Test 3 — each project's session state persists independently while the manager stays open.
4Open the Running menu.Since nothing is currently executing, it shows one disabled entry: <nothing running>.

Test 5 A running program shows in the Running menu, and Terminate stops it draft

Preconditions: gui_basics (09_gui_basics) registered.
#ActionExpected result
1Select the gui_basics tile, click Compile, check its one main, click Run selected.Output shows --- running <main> ---; since this program never exits on its own, Compile/Run selected stay disabled (busy) and Terminate becomes enabled; a separate small window belonging to the running Fearless program appears on screen.
2Open the Running menu.It now lists one live entry, formatted gui_basics - <main name>.
3Click that Running-menu entry.The manager selects/opens the gui_basics tile and panel — same effect as clicking the tile directly, confirming the menu is a shortcut to whatever is live.
4Click Terminate.Output appends --- terminating <main> ---, the child window closes, a final --- <main> exited with <code> ... --- line appears, the Running menu returns to <nothing running>, and Compile/Run selected re-enable.

Test 6 Closing the window (X) hides to the tray; Quit actually exits draft

Preconditions: Manager open, at least one project registered. Desktop has a system tray.
#ActionExpected result
1Click the window's native close button (X) in the title bar.The Manager window disappears, but the process is still running — a Fearless tray icon remains in the system tray.
2Double-click the tray icon (or right-click it → "Show manager").The Manager window reappears, restored (not minimized), in front, with every registered project and its state exactly as it was.
3Open Manager → Quit manager (or the tray icon's own "Quit manager").The window closes and the process actually exits — the tray icon disappears too, and nothing can be brought back short of relaunching the exe.

Test 7 Registering a folder nested inside an already-registered one is rejected draft

Preconditions: hello_world already registered.
#ActionExpected result
1Project → Add folder..., navigate inside the already-registered 01_hello_world folder (e.g. select its _hello subfolder) and confirm.No new tile is added. A warning dialog appears explaining that the folder can't be tracked because it's nested with an already-registered project, and names both folders.
2Dismiss the dialog.The icon grid is unchanged from before step 1 — nothing extra was added.

Test 8 Clear cache forces a recompile; Forget project removes only the manager's tracking draft

Preconditions: mains_in_methods registered and already compiled (e.g. continuing from Test 4 after compiling it once).
#ActionExpected result
1With mains_in_methods selected, Project → Clear cache.The Information panel's "Compiled cache" line flips from "up to date" to "needs compiling", and "Mains to run" reverts to <needs compiling> until Compile is pressed again. (This action doesn't print anything to Output.)
2Project → Forget project.The mains_in_methods tile disappears from the icon grid entirely, and the window falls back to the icon-grid-only view (same as before any tile was ever selected).
3Check the 02_mains_in_methods folder on disk.The project folder and its marker file are untouched — Forget project only removes it from the manager's own registered.txt, it deletes nothing on disk.

Open questions for review

  • Test 3 step 5 is the one place this document asks for a judgment call instead of a fact — is the current default Output size actually a problem in practice, or is scrolling fine for a first impression?
  • Should "clean start" be re-run before every test, or is chaining state forward across tests (as most of these do) acceptable, given a manager-restart step appears explicitly wherever it matters (Tests 1, 6)?
  • Anything from the current manager code this plan doesn't cover yet that should be in scope: sort order in the icon grid (Name/Modified/Compiled/Run), the elapsed-time status line at the bottom of the window, "Browse files", "Error report" for an invalid project, the rename-collision prompt when two folders would share a compact name?
